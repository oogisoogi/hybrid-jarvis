# 02 · 작업기억 4층 — 메모리·SOT·복원·TODO

에이전트 세션은 반드시 죽습니다. 컨텍스트가 차고, 재부팅이 오고, `/clear`를 하게 됩니다. 이 구조의 생존 원리는 하나입니다:

> **세션은 소모품, 작업기억은 디스크에.** 세션이 죽어도 다음 세션이 디스크에서 전 맥락을 복원한다.

## 4층 구조

| 층 | 파일 | 성격 | 갱신 시점 |
|---|---|---|---|
| 장기기억 | `memory/` + `MEMORY.md` 색인 | 반영구 규율·사실. 세션이 시작할 때 색인이 자동 로드 | 교훈이 생길 때 |
| 열린 과제 | `TODO.md` | "지금 뭘 해야 하는가" 단일 원장 | 실시간 |
| SOT | `SESSION_STATE.md` | 최근 상태·진행 서사·순환 스냅샷 | 작업 단위마다 |
| 복원 절차 | `RECOVERY.md` | 복원 순서·정상 기준선·시스템 스냅샷 | 주요 이벤트마다 |

### 왜 TODO와 SESSION_STATE를 나누는가

SOT는 커집니다(우리 실물은 수백 KB). 서사 속에 현재 과제가 묻히면, 복원한 세션이 "지금 뭘 해야 하는지"를 놓칩니다. 그래서 **열린 과제만 담는 얇은 원장(TODO)을 분리**하고 복원 시 이것을 먼저 읽습니다. 상세가 필요할 때만 SOT로 내려갑니다.

### 미결 항목의 필수 서식 — 해소 판정법

열린 과제를 적을 때는 반드시 한 줄을 함께 적습니다:

```
✗ 「기능 X 제거의 뜻 — 오너 답 대기」
   해소 판정: grep 'X' src/ 가 0건이면 해소
```

**왜**: 질문은 미해결일 때 적히므로 반드시 적히지만, 답은 "일이 실제로 일어난 곳"(코드·커밋·대화)에서 소비되고 원장에 안 남습니다. 세션이 압축되면 질문만 살아남고, 다음 세션이 **이미 답한 것을 오너에게 또 묻습니다**(하루 3회 오보 실증 후 박제된 규율). 판정법을 못 적겠으면 그 항목은 아직 질문이 덜 익은 것입니다.

## 복원 사이클

`/clear`·재부팅 후 복원 순서 (전문은 `templates/RECOVERY.md.template`):

1. 장기기억 색인 로드
2. **TODO.md 선독** (열린 과제 파악)
3. SESSION_STATE 최신 스냅샷 → RECOVERY 순서·기준선
4. **라이브 재점검** — 페인 목록·프로세스·uptime을 스냅샷과 대조
5. 각 페인 **resume 완전성 실측** — 프로세스 존재 ≠ 세션 기능. 화면을 직접 읽어 메뉴/승인 프롬프트에 멈춰 있지 않은지 확인
6. 무인 워처(모니터·센티널) 생존 확인 → **부재 시에만** 재가동 (중복 무장 금지 — 재무장 전 2경로 실측)
7. 인박스 갭 스윕 (3번 문서)
8. **전부-green 체크리스트 통과 후에만 복귀 보고** — "될 것"이 아니라 "확인했다"

### 자동화가 핵심이다

복원 절차를 "기억해서 수행"하게 두면 반드시 빠뜨립니다. 우리는 **SessionStart 훅**(`scripts/master-surface-pin.py`)이 `/clear`·재시작 직후 복원 지령을 컨텍스트에 자동 주입하게 했습니다. 어떤 입력이 오든 master는 복원부터 하고 응답합니다. 트리거 문구가 필요 없습니다.

훅은 이때 **결정론적 실측**도 함께 주입합니다: 미처리 인박스 헤더 수·줄범위를 코드가 직접 세서 넣습니다. master의 기억이나 절차 준수와 무관하게, 놓친 메시지가 있으면 숫자가 말해줍니다.

### 체크포인트 신선도 게이트

복원 문서(RECOVERY의 시스템 스냅샷)가 라이브와 모순되면 **라이브·SOT를 권위로** 하고 스냅샷은 stale 참고로 강등합니다. 낡은 스냅샷을 신뢰하면 복원이 오염됩니다. 실사고: 문서에 "교정 완료"라 적혔지만 실제 명령은 미실행이었고, 앱 재시작 후 며칠 전 세션이 부활했습니다. **"교정 완료"는 반드시 실측으로 확인합니다.**

## durable 갈무리 vs 결손 — 오보 금지

복원 시 다음은 "정상 갈무리 상태"일 수 있습니다: 함대가 빔 / 워커 페인 close / cron 부재 / 상주 페인 부재. **SOT의 의도 기록과 대조하기 전에는 이것들을 "갭·결손·문제"로 보고하지 않습니다.** 의도된 갈무리로 기록돼 있으면 "복원 정상·손실 0"으로만 보고합니다. 근거 없는 결손 오보는 오너의 신뢰를 갉아먹고, 다음 세션이 그 오보를 사실로 승격시키는 2차 사고를 만듭니다.

## 장기기억 운영 요령

- 메모리 1건 = 파일 1개 = 사실 1개. 색인(MEMORY.md)에는 한 줄 포인터만.
- **실측 근거 없는 진단은 '미확인'으로 명시** — 다음 세션이 사실로 승격하는 것을 막는 유일한 방법입니다.
- 이미 코드·git 이력이 기록하는 것은 저장하지 않습니다. 저장할 것은 "코드가 말해주지 않는 것"뿐.
- 틀린 것으로 판명된 메모리는 지웁니다. 낡은 규율이 자동 로드되면 그것이 다음 사고를 가르칩니다(8번 문서).
